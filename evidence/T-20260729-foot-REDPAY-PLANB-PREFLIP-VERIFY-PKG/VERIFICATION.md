## ② 예외 5케이스 조작 절차

### (a) 같은 금액 충돌
- **같은 환자 중복 선점**: 같은 (clinic, 환자)로 open 선점이 이미 있으면 부분 유니크 제약(23505) 위반 → 새 선점 생성 실패, 화면에 `이미 진행 중인 결제 선점이 있습니다. 기존 결제 완료 또는 만료 후 다시 시도하세요.` 표시. (`src/lib/paymentPlanb.ts:108-114` / 제약 `supabase/migrations/20260723180000_foot_redpay_planb_pending_payment.sql:51-52`)
- **다른 환자·같은 금액 동시 선점**: 같은 (clinic, 예상금액) open 선점이 2건 이상이면 **자동 매칭을 건너뜁니다**(모호 → 오배정 방지). 두 선점 모두 6분 뒤 만료(expired) → 수기입력 폴백. (`supabase/functions/redpay-planb-match/index.ts:94-102,126-127`)
- 조작: 별도 조작 없음. 충돌 시 자동 스킵 → 만료 → 수기입력.

### (b) 미배정 결제함 + [환자 연결]  → **[확인 불가 / 미구현]**
- **FE에 "미배정 결제함" 리스트도 "[환자 연결]" 다이얼로그도 없습니다.** (`src/` 전역 검색 결과 결제 관련 "미배정 결제함/환자 연결" UI 0건. `미배정` 문자열은 전부 *직원 배정*(Assignments/Staff/Reservations) 용도이며 결제와 무관.)
- 실제 동작: 매칭되지 않은 선점은 **PaymentPlanb 화면에서 "자동 기록되지 않았습니다 → [수기 입력하러 가기]"** 로만 안내됩니다(§③-4). 매칭 안 된 레드페이 원거래(raw)는 **기존 재조회 파이프(redpay-reconcile)** 와 **기존 분할결제 창의 수동 배정**으로 처리하도록 설계돼 있습니다(설계문서 언급, 전용 함 UI는 미구현).
- **→ 현장 확정문구 (d)와 근본 불일치. ON 前 정책 결정 필요**: (i) 문구를 실구현("수기 입력하러 가기")에 맞출지, (ii) "미배정 결제함 + [환자 연결]" 화면을 신규 개발할지.

### (c) 취소·환불  → **[부분 확인 불가]**
- PaymentPlanb 화면에는 **취소/환불 버튼이 없습니다.** (`src/pages/PaymentPlanb.tsx` 전량 확인)
- 상태값에는 `cancelled`(직원 중도취소)·`failed`(시스템/매칭 실패)가 정의돼 있으나(`src/lib/paymentPlanb.ts:41`), **FE에서 `cancelled` 를 발생시키는 클릭 경로는 코드에 없음**(=화면상 취소 불가, DB 수동 UPDATE로만 가능). **[확인 불가]** — 추정하지 않음.
- 환불: 선점(pending_payment)은 매출(payments)을 만들지 않으므로 **플랜B 자체엔 환불 개념이 없습니다.** 실결제/환불은 카드 단말(VAN)+기존 결제·환불 화면 소관.

### (d) 카드 분할결제  → **미지원(설계상 기존 화면 소관)**
- PaymentPlanb는 **단일 예상금액 1건**만 입력받습니다(분할 UI 없음). (`src/pages/PaymentPlanb.tsx:144-153`)
- 분할결제는 기존 결제 미니창(`[결제 등록]` → `onPayment`, `src/components/CheckInDetailSheet.tsx:2129-2136`) 소관.

### (e) 현금·이체 혼합  → **미지원(설계상 기존 화면 소관)**
- PaymentPlanb는 **결제수단 선택이 없습니다.** 레드페이(카드 VAN) 승인 raw 매칭 전용입니다. 현금/이체/혼합은 기존 결제 화면에서 수기 처리.

> ②(b)(c)(d)(e)의 공통 구조: **플랜B = "카드 단말 결제 → 예상금액 자동 매칭 → 자동 기록"** 한 가지 경로만 자동화. 그 외(취소/환불/분할/현금·이체)는 전부 **기존 화면 무접촉 유지**(EPIC §2 대원칙). 자동 실패 시 수기입력 폴백.

## ⑥ 피처플래그 ON/OFF + 롤백

### 켜고 끄는 법
- **플래그 이름**: `VITE_PAYMENT_PLANB` (환경변수)
- **판정 로직**: `src/lib/paymentPlanb.ts:32-38` — 값이 `on` | `1` | `true` 일 때만 ON. 그 외/미설정 = **OFF(기본)**.
- **적용 단위**: **전역(앱 전체) 1개** — 빌드/런타임 환경변수 단일 스위치. **자리별·직원별 개별 토글 불가**(코드상 per-자리/per-직원 분기 없음 — 확인됨).
- **켜기**: CF Pages 환경변수 `VITE_PAYMENT_PLANB=on` 설정 → **재빌드+재배포**(Vite build-time 주입). **끄기**: 값 제거 또는 `off` → 재빌드+재배포.
- **현재 prod 값**: **[확인 불가]** — CF Pages env 대시보드 접근 필요. 단 (i) 코드 기본값 OFF, (ii) 지금까지 flag OFF로 배포됨(커밋 기록 `1b88c094 … supervisor QA GO, flag OFF`).

### 3중 노출 차단(OFF일 때)
1. 진입 버튼 미렌더 — `src/components/PlanbPaymentEntryButton.tsx:24` (`return null`)
2. 결제 페이지 진입 즉시 `/admin` 리다이렉트 — `src/pages/PaymentPlanb.tsx:91`
3. 체크인 조회 쿼리 비활성 — `src/pages/PaymentPlanb.tsx:78`

### 롤백 절차
1. **1차(즉시)**: `VITE_PAYMENT_PLANB` OFF → 재빌드+재배포. → 진입 버튼 사라지고 페이지 접근 차단 = **신규 노출 0**. 직원은 기존 결제 화면만 보게 됨.
2. **선택(완전 무력화)**: 서버 배치 중단 `SELECT cron.unschedule('foot-redpay-planb-match');` (롤백 SQL: `supabase/migrations/20260729130000_foot_redpay_planb_match_cron.rollback.sql`). ※ open 선점이 없으면 배치는 어차피 no-op이라 필수는 아님.
3. **테이블/EF**: pending_payment 테이블·EF는 순수 ADDITIVE라 잔존해도 기존 흐름 무해 — 삭제 불필요.

### 기존 수기입력 + 폴러 흐름 무결 유지 (EPIC §2 대원칙) — 확인
- 플래그 OFF 시 진입 버튼 `null` → **기존 결제 화면(`[결제 등록]`)·수기입력 흐름 완전 무변경**(회귀 가드).
